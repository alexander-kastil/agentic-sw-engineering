# Azure DevOps Service Connections with Workload Identity Federation

Create/delete **Azure DevOps** service connections that authenticate to Azure via workload identity federation (WIF) with a **user-assigned managed identity**. No secrets, no keys, no cert rotation: OIDC trust between Azure DevOps and Entra ID.

**This is the Azure DevOps path.** For GitHub Actions OIDC (different issuer, different federated-credential subject, no service connection object), see [oidc-github-actions.md](oidc-github-actions.md) and [oidc-bicep.md](oidc-bicep.md).

| | Azure DevOps (this file) | GitHub Actions |
|---|---|---|
| Trust object | service connection (`serviceEndpoint`, ADO REST API `7.1-preview`) | federated credential on app/MI only |
| Issuer/subject | **auto-generated by Azure DevOps**, cannot be customized: query then sync | you author them (`repo:org/repo:ref:...`) |
| Consumer | pipeline `azureSubscription:` | `azure/login@v2` |

## Prerequisites

- Azure CLI + `azure-devops` extension
- Access to the target Azure subscription
- An Azure DevOps project
- `deploy.json` with the deployment metadata (sample: [../templates/deploy.json](../templates/deploy.json))

## Configuration: deploy.json

Scripts read metadata from `.github/deploy.json` in the repo root; never hardcode. Sample lives at `../templates/deploy.json`; the DevOps path additionally needs `ADOOrg` and `ADOProject`.

| Field | Meaning |
|---|---|
| `ResourceGroup` | RG where the managed identity is created |
| `WIF` | managed identity name prefix |
| `ADOOrg` | Azure DevOps organization URL |
| `ADOProject` | Azure DevOps project name |

```json
{
    "ResourceGroup": "your-resource-group-name",
    "WIF": "your-managed-identity-name-prefix",
    "ADOOrg": "https://dev.azure.com/your-org",
    "ADOProject": "your-project-name"
}
```

Example:

```json
{
    "ResourceGroup": "rg-agentic-sw-engineering",
    "WIF": "wi-agentic-sw",
    "ADOOrg": "https://dev.azure.com/integrationsonline",
    "ADOProject": "agentic-sw-engineering"
}
```

Edit `.github/deploy.json` before running for a different environment.

## Create

Script location: `demos/03-release-strategy/01-release-pipelines/01-service-connections/`

PowerShell (recommended default; Windows, WSL, PowerShell 7+ on Linux/macOS):

```powershell
cd demos/03-release-strategy/01-release-pipelines/01-service-connections
.\create-workload-identity.ps1
```

Bash (Linux, macOS, Git Bash):

```bash
cd demos/03-release-strategy/01-release-pipelines/01-service-connections
bash create-workload-identity.sh
```

### What the create script does

| # | Step | Detail |
|---|---|---|
| 1 | Load config | `ResourceGroup`, `WIF`, `ADOOrg`, `ADOProject` from `.github/deploy.json` |
| 2 | Create resource group | region `westeurope` (customizable in script) |
| 3 | Create managed identity | named from `WIF` prefix, system-assigned access |
| 4 | Wait 15s | service principal backing the MI must replicate (eventual consistency) |
| 5 | Assign Contributor | to the MI at resource-group scope |
| 6 | Create service connection | ADO REST API `v7.1-preview`, WIF authorization scheme, bound to the project |
| 7 | Detect issuer/subject | query the connection, parse `workloadIdentityFederationIssuer` + `workloadIdentityFederationSubject` (ADO generates these; not settable via API) |
| 8 | Create federated credential | on the MI, using the queried issuer/subject. **Critical: without it ADO cannot authenticate** |
| 9 | Share connection | with all pipelines in the project |

### Issuer/subject is a three-step sync

1. Create the service connection (ADO auto-generates issuer/subject).
2. Query the service connection for the actual values.
3. Create/update the federated credential to match.

This keeps the credential aligned with what ADO expects even when the generated values differ from what was anticipated.

**Project reference:** the payload needs both project **ID** and **name** in `serviceEndpointProjectReferences`; the scripts look the ID up.

## Delete

Same folder. Bash version recommended.

```bash
cd demos/03-release-strategy/01-release-pipelines/01-service-connections
bash delete-workload-identity.sh
```

```powershell
cd demos/03-release-strategy/01-release-pipelines/01-service-connections
.\delete-workload-identity.ps1
```

### Deletion order (dependency-critical)

1. **Federated credential** (on the MI) first: Azure blocks service-connection deletion while it exists.
2. **Azure DevOps service connection**.
3. **Role assignments** (Contributor off the MI).
4. **Managed identity**.
5. **Resource group**, optional, interactive prompt; retained if declined.

## Scenarios

| Scenario | Steps |
|---|---|
| New dev connection | run create script -> verify in ADO Project Settings -> Service connections -> verify federated credential (Portal -> Managed Identities -> identity -> Federated credentials) -> run a sample pipeline |
| Clean up test resources | run delete script -> optionally confirm RG deletion -> verify in Portal + ADO UI |
| Migrate SP auth -> WIF | create WIF connection -> test in a new pipeline/test env -> confirm secretless auth -> delete old SP connections -> repoint all pipelines |
| Per-environment connections | run create with env suffix (`wi-az400-test`, `wi-az400-prod`) -> verify isolation/sharing -> use per-env connection in each pipeline |

## Troubleshooting

| Error / warning | Cause | Fix |
|---|---|---|
| `Following fields in the service connection are not expected: workloadIdentityFederationAudience` | setting custom issuer/subject values ADO does not support | scripts never set custom values, they query and sync; verify the run completed all steps |
| `Cannot delete this service connection while federated credentials for app {...} exist in Entra tenant` | delete script interrupted/partial | re-run the delete script: it removes the federated credential first |
| `Waiting for service principal propagation... (10/10)` | SP not replicated yet (eventual consistency) | scripts retry 10x / 10s; usually self-resolves, else wait 5 minutes and retry |
| `Retrying role assignment... (5/5)` | role-assignment propagation delay or permission gap | scripts retry 5x / 5s; verify your account may assign roles at subscription level |
